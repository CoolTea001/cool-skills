# 代码优化 Skill

## 目标

在**不改变外部可观察行为**的前提下，优化代码的规范、逻辑和可读性，使代码更清晰、一致、可维护、可验证。

默认优化顺序：

1. 正确性与安全性
2. 行为不变
3. 可验证性
4. 可读性
5. 项目一致性
6. 性能（仅在测量后，且单独处理）

## 适用场景

- 用户说“优化这段代码”“重构一下”“清理坏味道”
- 用户要求提升可读性、可维护性
- 用户要求统一命名、格式、错误处理、类型
- 用户要求减少重复、降低嵌套、拆分长函数
- 用户要求让代码更符合项目现有风格

## 不适用或必须先确认

- 需要改变公共 API、数据库 schema、配置格式、返回结构
- 需要改变业务规则、错误语义、副作用顺序
- 需要升级依赖、替换框架、大规模重命名
- 没有测试且无法验证行为
- 用户只是说“优化”，但没给范围

遇到以上情况：先说明风险，提出小范围方案，必要时询问用户。

## 核心原则

1. **先读再改**：读 README、配置、相邻代码、测试、调用方。
2. **行为不变优先**：默认只改内部质量，不改外部行为。
3. **小步原子**：一次只处理一个主题，保持 diff 可 review。
4. **验证驱动**：能跑测试就跑；不能跑就明确说明。
5. **最小改动**：不做无关格式化、重命名、依赖升级。
6. **遵循项目惯例**：命名、目录、导入、类型、错误处理都先看现有代码。
7. **可读性优先于聪明**：显式优于隐式，简单优于炫技。
8. **不掩盖错误**：不空 catch、不滥用 any、不关 lint 规则。
9. **不过早抽象**：重复三次以上、概念稳定、能命名，再抽象。
10. **不确定就问**：不要猜业务规则、兼容性要求和隐藏调用方。

## 工作流

### 1. 侦察

先收集信息，不要直接动手：

- 语言、框架、版本、包管理器
- 格式化、lint、类型检查、测试命令
- 目录结构和模块边界
- 公共 API、导出接口、调用方
- 现有命名风格、错误处理风格、日志风格
- 当前测试是否通过

如果项目有测试，先运行基线测试。若基线失败，记录哪些是原有失败。

### 2. 定义边界

明确：

- 这次优化什么？
- 不改什么？
- 验收标准是什么？
- 是否需要保持行为完全不变？
- 是否允许改变内部接口？

如果用户要求模糊，给出一个最小优化范围并确认。

### 3. 制定小步计划

按优先级列出 3～7 个小步骤，例如：

1. 提取魔法值为常量
2. 用早返回降低嵌套
3. 重命名泛化变量
4. 提取重复校验函数
5. 补充错误上下文
6. 运行测试和类型检查

每一步都应能独立解释、独立回滚。

### 4. 逐项修改

修改时遵守：

- 一次只处理一个坏味道
- 不混合格式化与逻辑改动
- 不顺手改无关文件
- 保持原有注释意图，删除过时注释
- 删除死代码前先搜索引用
- 修改公共接口时同步更新调用方、测试、文档

### 5. 验证

按项目实际情况运行：

- 单元测试 / 集成测试
- 类型检查
- lint / format
- 构建
- 手动验证关键路径
- 检查 diff 是否只包含预期改动

如果无法运行，必须说明：为什么不能、风险是什么、建议用户运行什么。

### 6. 报告

报告要真实、简短、可操作。不要写“已完成”但不给证据。

## 优化检查清单

### 代码规范

- [ ] 命名符合项目风格，且表达业务含义
- [ ] 没有 `data`、`temp`、`obj`、`flag` 这类泛化命名
- [ ] 导入无未使用、无通配符、无循环依赖
- [ ] 类型明确，没有滥用 `any`、`Any`、`# type: ignore`
- [ ] 魔法值已提取为常量、枚举或配置
- [ ] 注释解释“为什么”，不是重复“是什么”
- [ ] 错误处理有上下文，没有空 catch
- [ ] 函数和文件职责单一
- [ ] 没有无关格式化噪音

### 代码逻辑

- [ ] 处理了空值、零、负数、超长、超时、并发、权限等边界
- [ ] 使用早返回或 guard clause，避免深层嵌套
- [ ] 重复逻辑已提取，但没有过度抽象
- [ ] 副作用显式，函数名能体现会写库、发请求、改状态
- [ ] 资源在异常路径也能释放
- [ ] 异步调用正确 await，错误被处理
- [ ] 数据转换中 `null` / `undefined` / 空字符串 / 0 语义清晰
- [ ] 没有循环查库、N+1 请求等明显问题
- [ ] 业务规则没有散落在多层
- [ ] 外部输入有校验

### 代码可读性

- [ ] 函数短小，单一职责
- [ ] 变量作用域小，没有反复复用
- [ ] 没有过早抽象
- [ ] 没有一行多语句、复杂嵌套三元、超长链式调用
- [ ] 模块边界清晰，没有万能工具模块
- [ ] 错误信息包含操作、对象、关键参数
- [ ] 死代码和注释代码已清理
- [ ] 测试名能说明行为，测试验证核心逻辑而非全是 mock

## 坏味道 → 修复映射

| 坏味道 | 优先修复方式 |
|---|---|
| 长函数 | 提取有意义的子函数，保持单一职责 |
| 深嵌套 | 早返回、guard clause、提取条件函数 |
| 重复代码 | 提取函数/常量/策略，但避免过早抽象 |
| 泛化命名 | 改成业务含义明确的命名 |
| 魔法值 | 常量、枚举、配置 |
| 空 catch | 处理、添加上下文、重新抛出或记录 |
| 滥用 any | 补类型；临时隔离并标注原因 |
| 硬编码 | 配置化，但不要过度配置 |
| 循环查库 | 批量查询、预加载、缓存 |
| 全局状态 | 显式参数、依赖注入 |
| 废话注释 | 删除；需要时写“为什么” |
| 大 diff | 拆成多个小 commit，分离格式化和逻辑改动 |

## 决策规则

- **何时抽象**：重复 ≥ 3 次、概念稳定、能起好名字、未来变化方向一致。
- **何时不抽象**：只出现一次、命名困难、只是“以后可能用”。
- **何时改变行为**：用户明确要求，且更新测试、调用方、迁移说明。
- **何时不优化**：没有测试且无法验证，先补测试或缩小范围。
- **何时停止**：diff 开始变大、目标变模糊、出现无关改动。

## 禁止事项

- 不运行验证就说“已完成”“测试通过”
- 为了让测试变绿而删测试、改断言、加 skip
- 空 catch、吞异常、滥用 any 逃逸类型
- 大规模格式化、重命名、重构混在一次修改里
- 改公共接口不更新调用方
- 为小问题引入新依赖
- 过度抽象、过度设计
- 顺手改无关文件
- 猜测业务规则并直接实现
- 删除看似无用但可能被动态引用的代码

## 快速自检

每次修改后问自己：

1. 我读了上下文吗？
2. 我能解释每一处改动吗？
3. 外部行为是否保持不变？
4. 命名是否表意？
5. 是否消除了重复、魔法值、深嵌套、空 catch？
6. 是否运行了可用的验证？
7. diff 是否最小且聚焦？
8. 是否更新了测试、文档或调用方？
9. 有没有引入新的过度抽象？
10. 如果我是 reviewer，我会不会批准这个 diff？
